# 首轮数据库迁移与恢复约定

日期：2026-11-12。已覆盖G0基线、可靠开始探索v2、MC-1A配置版本v3，以及B2持久连通测试v4。未操作既有业务库。验证结果以 [STATUS](STATUS.md) 为准。

## 版本与执行

- `internal/store/schema.sql` 固定为版本1：原有 Mission/Thread/Attempt/Action/Observation/Event、约束、索引和动作不可变触发器。后续不要修改其内容，新增变化追加迁移。
- `internal/store/migrations/002_operations.sql` 为版本2：新增提交回执和不可变触发器；不重判或更新旧动作。
- `internal/store/migrations/003_model_configs.sql` 为版本3：配置头、不可变加密版本和默认选择；不改旧研究/动作/提交回执。主密钥不入库，需与数据库分别保护和备份；没有在线主密钥轮换或历史凭据删除接口。丢失主密钥不能解密，错误密钥不当成空配置；主入口在Recover/调度前校验现有配置可解密。
- `internal/store/migrations/004_model_tests.sql` 为版本4：全局测试ID、精确配置版本外键、固定用途/请求版本、pending/running/completed与不可变终态；不保存供应商内容或秘密。未完成队列容量由持锁事务限制；Recover将未完成测试标为unknown，不自动发送，保留历史回执用于核对。
- `wscyber_schema_migrations` 记录 version、SQL SHA256、applied_at。Open 先持有既有数据库级单实例 advisory 锁，再检查历史版本/校验值，按顺序执行缺失迁移。发现未知版本、缺口或已应用 SQL 被修改时拒绝启动。
- 无版本表的既有 G0 安装先运行幂等版本1并登记，再依序应用版本2、3、4；不删除、重建或清空业务表。这个路径只承接已知基线，不是任意第三方或手工改表后的自动修复器。校验值验证迁移文件历史，不是数据库全结构漂移检测。
- 版本登记和本次所有结构变更在同一事务提交；失败整体回滚，不留“已登记但未应用”版本。DDL 锁等待上限2秒，主入口启动上下文上限20秒；错误时不启动调度。
- 后续重启只检查已应用版本，不再每次重建旧触发器；Recover 仍由主入口在迁移成功后调用。迁移不取代恢复，恢复仍将可能已发送的 running Action 标为 unknown，不重放。

## 升级前后步骤

1. 停止接收新任务并正常停止旧控制面，确认没有遗留执行器；暂停不是撤回在途请求，不依据界面关闭推断已经停止。
2. 由管理员对**明确属于本项目**的数据库做 `pg_dump -Fc` 备份，妥善保护材料与数据库连接凭据；不要把连接串、令牌或备份提交到 Git，也不要把业务库秘密写入命令历史/文档。留存匹配的旧程序和配置版本。
3. 先在新建隔离库用 `pg_restore --exit-on-error` 恢复备份，核对业务记录、原始字节、归属、暂停/预算、待审与 unknown，再以新程序验证升级。禁止把其他项目的库、卷或服务用作测试资源。
4. 获得实际部署授权后才启动新控制面应用迁移。本开发轮次没有升级业务库、重启既有应用或修改私有配置。
5. 确认版本1/2/3/4、已有记录与约束仍在，检查实时 Snapshot/事件，再决定恢复任务；不要通过测试请求误启动真实目标。

## 失败与回退

- 迁移失败时保持服务停止，先查结构/版本/锁问题，不能删库重建、手动伪造迁移成功、改写已应用校验值或批量放行 pending。
- 没有自动 down migration。需要回退时，停止新实例，将已核验备份恢复到新的明确隔离位置，再用匹配旧程序验证并按部署流程切换。不要让旧二进制直接访问已升级库；旧版本没有新版本校验能力。
- **成功启动后的外部效果不能被数据库回滚撤销。** 升级后若有新任务/动作，不得直接用旧备份替换当前库，否则会遗失提交键和证据、可能把旧请求当新请求再执行。先保存当前完整数据并核对所有在途/unknown，再单独制定恢复方案。
- operations 成功回执不可更新/删除、不自动过期；当前没有数据清理接口。未来清理必须设计墓碑/失效键拒绝机制，不能删除后允许旧键重新启动。
