# 界面设计需求说明（给设计师，2026-11-20）

本文交给专业设计师出 **高保真稿**。首批两页：**总览**、**漏洞卡（漏洞详情）**；外壳与漏洞列表只作为上下文，可顺带统一风格。设计稿回来后由开发按稿实现。本文只规定 **要放什么、优先级、区域划分与交互**；视觉风格、配色细节、图标与插画由设计师决定。

## 0. 产品与用户

**产品**：集团内部的 Web/API 安全测试平台。AI 在授权范围内自主探索目标系统，平台保存每个真实请求/响应作为证据，AI 提出“候选漏洞”，再由独立的 AI 会话重新取证验证，最后形成漏洞、推送企业微信、对接内部 SDL 工单、复测关闭。

**主要用户与场景**：
| 用户 | 一天里做什么 | 最关心 |
|---|---|---|
| 安全研究员（主用户） | 看 AI 跑出来的漏洞，确认/定级/派给研发；补测试信息；盯逾期 | 今天要处理什么；漏洞到底是不是真的、核心是什么 |
| 安全负责人 | 每周看整体风险与修复进度 | 未修复高危有多少、谁逾期、趋势 |
| 研发（经 SDL 工单或分享链接查看漏洞卡） | 看懂并复现漏洞，修完申请复测 | **10 秒看懂、1 分钟复现** |

**设计原则**：
1. **结论先行**：每页最上面回答“要不要我处理、处理什么”。
2. **漏洞的本体是“最小复现”**：1–3 个关键请求 + 一句话影响；AI 的长篇推理放附录折叠，不在首屏。
3. **证据真实**：HTTP 请求/响应原文以等宽字体完整展示，可高亮关键行，不做美化改写。
4. **信息密度适中**：这是每天使用的专业工具，偏向 Linear / Datadog / GitHub 的密度，而不是营销页。
5. 状态、等级、处置三个维度各自独立（见 §3 枚举），视觉上不要混成一个颜色。

## 1. 技术与交付约束

- 实现基于 React + Tailwind，组件体系类似 shadcn/ui（Button、Badge、Select、Dialog、Sheet、Tabs、Table、Tooltip）。请尽量使用这类常规组件的形态，自定义组件需单独标注状态。
- **字体**：中文 Noto Sans SC / PingFang SC，英文与数字 Inter；代码与 HTTP 原文 JetBrains Mono。数字一律等宽对齐（tabular）。
- **画布**：桌面 1440×900 为主稿；需说明 1280 宽时的取舍；另出一张 ≤768 宽（平板/手机查看漏洞卡，研发常在手机上看推送链接）的漏洞卡稿。
- **主题**：浅色、深色各一套（当前产品默认深色与浅色都在用）。请以设计 Token 形式给出颜色（背景/卡片/边框/文字层级/主色/状态色/等级色），开发会映射到 CSS 变量。
- 中文界面为主，文案长度按中文设计；英文界面只需保证不破版。
- **交付**：Figma（或同类）源文件 + 标注；组件状态（默认/悬停/选中/禁用/加载/空/错误）；颜色与字号 Token 表。

## 3. 枚举与语义色（请给出完整配色）

| 维度 | 取值 | 说明 |
|---|---|---|
| **状态**（平台根据验证/复测自动得出） | 新发现 / 仍存在 / 待验证 / 未支持 / 已修复 | 新发现最醒目；未支持=验证未能证实 |
| **等级**（人工定，后续 AI 给“建议”） | 严重 / 高危 / 中危 / 低危 / 信息 / 未定级 | 另需“AI 建议等级”的弱化样式（虚线框或浅色） |
| **处置**（人工） | 待处理 / 修复中 / 接受风险 / 误报 | 误报需整体弱化 |
| **期限** | 正常 / 即将到期（≤2 天）/ 逾期 N 天 | 逾期为红 |
| **工单**（SDL 对接后） | 未提交 / 已提交 / 研发处理中 / 已修复待复测 / 已关闭 / 打回 | |
| **验证判读** | 支持 / 反证 / 证据不足 | AI 判读，需带“模型判读”弱标签 |
| **复测结论** | 仍可复现 / 已修复 / 无法判定 | |

## 4. 总览页（首批高保真）

目标：研究员早上打开 30 秒内知道 **今天要处理什么**；负责人一眼看到 **风险与修复进度**。

```
页头：总览 ·（时间范围 7/30/90 天）……………………………………… 刷新 · [新建任务]
┌ A 待我处理（整行，最高优先级）───────────────────────────────────────────┐
│ 横排 5–6 个“待办卡”，每个：数字 + 名称 + 一句说明 + 点击进入已筛选列表    │
│ 待定级的新漏洞 · 待确认推送 · 待审批操作 · 已逾期 · 研发申请复测 ·      │
│ 测试信息待补的资产（来自 SDL 申请单同步）                               │
│ 数字为 0 的卡弱化；全为 0 时显示一行“今天没有待处理事项”               │
└────────────────────────────────────────────────────────────────────────┘
┌ B 风险态势（2/3）────────────────────────┐┌ C 修复进度（1/3）──────────┐
│ 未修复漏洞按等级：严重/高/中/低 大数字     ││ SLA 达成率（%）            │
│ 下方：按日趋势（新发现/仍存在/已修复堆叠）  ││ 平均修复时长（天，按等级）  │
│                                          ││ 逾期 Top5（标题·负责人·逾期天）│
└──────────────────────────────────────────┘└────────────────────────────┘
┌ D 测试运行（1/3）────────┐┌ E 资产覆盖（1/3）──────┐┌ F 最近确认（1/3）────┐
│ 运行中任务（进度/已用时）  ││ 近 30 天已测/未测资产    ││ 最近 5 条新确认漏洞   │
│ 即将运行的周期计划 ≤5     ││ 比例 + 最久未测 Top5     ││ 等级·标题·资产·时间   │
│ 最近失败的运行（醒目）     ││                         ││                     │
└──────────────────────────┘└────────────────────────┘└─────────────────────┘
┌ G AI 资源（整行，低优先级，可折叠）：Token 按日柱状 · 区间合计 · 按任务 Top5 ┐
└────────────────────────────────────────────────────────────────────────────┘
```
- A 区最重要，视觉权重最高；G 区最低。
- 每张卡标题行右侧“查看全部 →”。
- 需要设计：加载骨架、空数据（新部署时几乎全空）、单卡出错（只该卡显示错误与重试）。
- 示例数据请用中性虚构内容（如“订单服务”“会员中心 API”“GET /api/orders/{id}”），不要用真实系统名。

## 5. 漏洞卡（漏洞详情，首批高保真）

一个漏洞的唯一权威视图。研究员在这里确认、定级、派单；研发通过 SDL 工单链接打开同一页面（只读视图，隐藏内部操作）。入口：漏洞列表行点击、总览、企业微信推送链接、SDL 工单链接。

**布局（1440）**：主栏（约 2/3）+ 右侧信息栏（约 1/3，固定宽 360–400，随页面滚动吸附）。

```
顶栏：← 返回漏洞列表 · 面包屑（资产 / 漏洞） …………… [上一条][下一条]
┌ 标题区（整宽）──────────────────────────────────────────────────────────┐
│ [等级徽章 高危] 标题（模板化：资产 · 接口 · 漏洞类型，例：               │
│ “会员中心 API · GET /api/orders/{id} · 越权读取他人订单”）              │
│ 状态徽章 · 处置徽章 · 期限（逾期 3 天）· 编号 VULN-0123 · 首次发现时间     │
│ 主操作（右侧）：[提交工单]（主按钮） [一键重放] [复制 curl] […更多]       │
└─────────────────────────────────────────────────────────────────────────┘
┌ 主栏 ───────────────────────────────────────┐┌ 右侧信息栏 ──────────────┐
│ ① 一句话影响（大字号，1–2 行）               ││ 处置（可编辑表单）        │
│   “普通用户可通过修改订单 ID 读取任意用户的    ││  等级（含 AI 建议）        │
│    订单详情，含手机号与地址。”                 ││  处置 · 负责人 · 修复期限  │
│ ② 前置条件：需要任意普通用户账号               ││  备注                     │
│ ③ 关键请求（核心，1–3 个，编号步骤）           ││ ───────                   │
│   每个：步骤说明一行 + 请求/响应左右并排        ││ 工单（SDL）               │
│   （窄屏上下），等宽原文，关键行高亮，          ││  状态 · 工单号链接 ·       │
│   过长折叠“展开全部”；右上角：复制 / 截图 /     ││  研发负责人 · 最近同步     │
│   在流量中查看                                 ││ ───────                   │
│ ④ 对照（越权类必有）：正常身份/正常参数下的     ││ 资产                      │
│   请求与响应，与③并排或差异高亮                 ││  名称 · 环境 · 负责人 ·    │
│ ⑤ 修复建议（≤3 条要点）                       ││  授权范围                  │
│ ⑥ 复测方法：重放步骤 3，期望返回 403            ││ ───────                   │
│   [申请复测] 最近复测结论                       ││ 生命周期时间线（竖向）     │
│ ─────────────────────────                    ││  发现 → AI 验证支持 →      │
│ ⑦ 附录（默认全部折叠）                         ││  人工定级 → 推送企业微信 → │
│   · AI 验证记录（判读、方法、局限）             ││  提交工单 → 研发修复 →     │
│   · AI 研究过程摘要（可跳到完整执行记录）       ││  复测已修复 → 关闭         │
│   · 全部证据列表（n 条）                       ││  每个节点：时间·操作人      │
│   · 关联候选（跨多轮任务发现的同一问题，n 个）   ││ ───────                   │
│   · 变更记录（谁改了等级/处置）                 ││ 相关：同资产其他漏洞 ≤5    │
└──────────────────────────────────────────────┘└──────────────────────────┘
```
- **①③是首屏核心**：1440×900 首屏内应能看到一句话影响 + 第一个关键请求的请求与响应开头。
- 关键请求的展示是本产品的“招牌”，请重点设计：方法与路径醒目；请求头可折叠（默认只显示关键头）；响应体关键片段高亮（例如他人的手机号字段），非关键部分弱化；支持“遮盖敏感值”开关。
- 研发只读视图：隐藏处置编辑、提交工单等内部操作，保留复制 curl、一键重放（若有权限）、申请复测；顶部加一条说明条“安全团队提交 · 有疑问联系 xx”。
- ≤768 宽：右侧栏移到标题区下方，变为可折叠分组；请求/响应改为上下排列，可横向滚动。
- 需要设计的状态：AI 未给出最小复现时（显示“完整证据”列表与“生成最小复现”按钮）、误报（整体弱化 + 顶部说明条）、已修复（顶部绿色说明条 + 复测证据）、加载、无权限。
