# 已确定：以 cyber-harness 为平台底座

2026-11-13。**这是用户已明确的架构决定，不再是候选选型；尚未完成代码迁移或运行接入。** 本文优先于旧A3/E1中继续扩写自研Harness、保留旧Decision循环作为新运行底座的描述。现有代码和历史验证仍是事实，但不等于新架构方向。

**实施授权更新：** 用户已明确直接开始开发，按原生机制复用/扩展，功能与执行细节允许只读登录Cyber学习。首轮H1已完成显式本机原生运行链的定向验证；当前及后续短片以STATUS为准，平台业务/原生UI仍待逐片接线，功能按独立短轮推进，重型串行、不全量测试，每轮交回后清理本轮专属资源并正常退出再开新会话。准确实施状态以STATUS最新段为准，不把开工授权写成已接通。

## 1. 用户决定

> 全部基于cyber harness这个harness架构上来实现之前的功能设计，不再使用自己新建harness；直接使用现成轮子，能复用的直接复用，在它基础上实现额外功能需求。

因此：

- **Cyber是平台主体底座，不是可选执行插件。** 不再讨论“继续自研Harness还是采用Cyber”，也不把仅套一个API wrapper当完整落实。
- Agent运行循环、会话、工具/上下文/事件等通用运行能力，直接采用上游已有实现；不再在wscyber另建同职责Harness。
- 额外平台需求优先通过其真实扩展机制实现。可持有必要业务数据和接口，但不在业务层重造逐轮模型决策/工具调度引擎。
- 不保留旧Snapshot→Decision循环再逐步指挥Cyber，不让同一执行由两套循环、状态和恢复逻辑同时控制。
- “能复用就直接复用”包括运行与交互能力。原生协议客户端、终端、日志、流量和合适的UI组合应纳入复用核验，而不是只仿配色。旧Ant组合、路由、表结构和自研引擎都不是必须保留的上位限制。

## 2. 原有需求保留，实现方式改为原生能力加扩展

此前产品设计仍是需求来源，见product-confirmation.md、research-configuration.md、findings-and-reporting.md及task-interaction-backlog.md。功能是否已实现仍以STATUS/API/代码为准；下表不声称Cyber已全部满足或平台已完成迁移。

| 用户价值 | 基于Cyber的实现原则 |
|---|---|
| 自主安全研究、按需工具/Skill/协作 | 复用原生运行能力，不再自写通用Agent循环 |
| 任务、目标授权、身份/业务前提、操作控制 | 映射原生任务/会话与控制语义，缺口用平台扩展补齐；不靠模型提示扩大授权 |
| 真实执行输出、终端、日志、HTTP请求/响应 | 优先复用原生事件、终端和流量底座及其交互，保持证据归属、原件与捕获边界 |
| 候选发现、稳定编号、独立验证、复测 | 在原生执行上实现平台成果扩展，不把模型自报或普通工具结果直接当已确认漏洞 |
| 任务内对话、方向调整、发现时间线/图谱 | 依据原生会话/事件与真实关联做扩展；操作生效、只读查询与触发执行分清 |
| 模型配置/用量、资料库、模型原文开关 | 能用原生能力则直接用，再补用户需要的策略与业务视图，不保留两份互相冲突的配置权威 |
| 报告、外部SDL与双向复测对接 | 按既有产品目标在此底座上分片扩展，生成/发布/投递与测试执行分开 |

不因上游页面暂时没有某入口就删除用户需求，也不因为用户要求有该功能而用假数据/假日志/占位操作冒充已实现。

## 3. 开发与复用边界

- 先逐项核对“需求 → 原生能力 → 实际扩展点 → 需新增的业务功能 → 验证方法”，不再作是否使用Cyber的架构二选一。
- 当前静态评估已指向Extension、Web Capability和前端Slot/组合机制；具体生命周期与接口必须以固定版本源码核验，不能从“一切可扩展”推断任意功能零改动可用。
- 扩展点不足时先记录具体缺口和必要补丁，不能默认绕到另一套自研Harness。尽量保持可跟随上游升级的扩展边界。
- 原生运行事实由其对应记录负责；平台额外业务对象有明确所有者，需要投影时可重建，不双写两份会独立决定执行真相的状态。
- 现有wscyber代码作为需求、业务规则、证据处理与回归资产逐项复用或替换；不为保留旧实现而扭曲新底座。旧数据/编号/证据不能无计划删除或重建，同一任务不能被两套引擎同时派发。
