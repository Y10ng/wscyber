## 1. 产品目标

独立、自托管、面向明确授权场景的安全研究平台。目标是具备优秀的漏洞挖掘、代码审计、CTF 和内部攻防演练能力，并将可复核的发现转化为有稳定编号的漏洞记录、模型辅助报告及内部 SDL 流程输入。

核心不是固定扫描流水线，也不是逐步审批 Agent 的工作，而是：**围绕问题自主探索，及时保存证据，按需协作，在实际出站请求处控制风险，依据证据形成可交付成果。**

“优秀”需要在可比目标、模型、预算与授权条件下证明，不由 Agent 数量、框架名称、工具数量或上游宣传指标保证。当前工程基线没有完成这种效果验证。

## 2. 通用内核与场景模式

保留 Go 控制面、持久研究状态与可替换适配器。借鉴共享研究上下文、证据累积、机会驱动调度和按需分工的思想；**不强制采用名为“黑板”的架构，不预建固定多层专家组织**。

| 场景模式（目标） | 主要输入与研究方式 | 交付与边界 |
|---|---|---|
| 漏洞挖掘 / 授权渗透测试 | 业务背景、身份、接口与授权目标；提出假设、验证与反证 | 可复核发现、请求/响应证据、影响与修复建议；不扩大目标范围 |
| 代码审计 | 获准分析的仓库版本、构建背景、源码位置；静态线索与必要受控验证 | 绑定 commit/路径/位置的发现与证据；源码不因审计自动获准上传模型或执行构建脚本 |
| CTF | 明确比赛/靶场范围、规则、题目与材料；按题型选择工具和验证方法 | 解题证据、过程与可复现结论；不自动提交 flag，不把题目成果冒充生产漏洞 |
| 内部攻防演练 | 演练授权、资产/身份范围、时间窗口、行为限制与停止条件 | 可追溯验证链、发现及防守改进建议；多阶段行为仍受逐请求控制，不默认放开破坏性或范围外行为 |

不同模式共享研究、执行、证据、发现和报告内核，通过**版本化场景 Profile**配置目标、提示词、工具能力集合、上下文选择、证据要求、验证准则和报告模板。提示词可以规范工作方式，**不能授予权限或替代程序控制**。各场景默认共享已有工具与联网能力；切换模式不扩大目标授权或提高预算，也不会安装缺失工具。版本化 Profile 尚未实现。

不把一切差异都塞进提示词：代码位置、HTTP 证据、CTF 结果和演练时间约束使用明确的数据/适配契约；不为每个场景再造一套调度器和数据库。

## 3. 审批只针对需要拦截的实际目标请求

用户明确要求：Agent 可以自主探索；如测试删除功能时准备发送危险 `/delete` 请求，应在到达目标前拦截。**不审批探索意图、每次推理或每个工具调用，也不默认逐命令审批。**

推荐出口策略为：

1. **allow：自动放行**授权范围内且策略允许的请求。
2. **review：拦截待审**命中危险信号或明确要求人工判断的请求，不把所有未识别请求一律送审。
3. **deny：拒绝**越界或明确禁止的请求；人工放行不能绕过硬授权边界。

风险结合方法、规范化 URL、参数、请求体、身份/会话与业务语义判断。GET 不等于安全，路径不包含 delete 也可能删除数据；不接受 Agent 自报“安全”作为最终放行依据。模型可以辅助分类，但不能改写策略或自批请求。

一次工具调用可能产生多个请求，必须检查实际请求，不能批准一次命令就放过后续所有流量。审批绑定具体请求及有效执行上下文；修改参数、会话失效或规则变化后需重新检查。人工只处理被拦截项，正常探索不变成工单流水线。

目标出站流量控制、模型数据出境和报告发布是不同边界。选择模型或 SDL 连接器不是允许发送所有材料；敏感数据和外部发布按明确配置与授权控制，但不借此重新引入逐步探索审批。

**G0 现状：新 `local_command` 默认 approved；平台 HTTP 的 `request-signals-v1` 在 DELETE 及 URL/path/query/body/JSON、method override 中识别 delete/remove 等明确破坏信号，命中才 pending，其余默认 approved。** 这不是完整业务风险分类，未知不一律待审；历史 pending 不自动重评或放行。平台 HTTP 保留 origin/DNS 硬校验；命令网络默认 bridge，可显式设为 none，但直连流量尚未拦截或强制 origin。G0 不是完整 G1/原生代理，详见 [architecture](architecture.md)。

## 4. 研究与证据工作模型

| 对象 | 解决的问题 | 不能混同 |
|---|---|---|
| Mission / Scope / Profile | 为什么研究、研究什么、允许在哪里以何种方式进行 | 背景、场景提示词与硬授权 |
| Thread | 长寿命问题、依据、假设、下一步与未决事项 | 一次模型会话或容器 |
| Attempt / Work item | 有限的计算与执行尝试、按需分工及结果交回 | 问题已解决或必然有发现 |
| Tool action / Outbound request | 工具任务与实际网络请求；一个工具可产生多个请求 | 工具获准使用与每个请求获准发送 |
| Observation / Evidence | 观察、原始材料及其来源、引用、捕获边界 | 模型陈述与已证实事实 |
| Finding / Verification | 有稳定身份的候选发现与实质验证记录 | 有编号就代表漏洞成立 |
| Report / Delivery | 基于固定证据版本生成报告、导出与 SDL 投递 | 生成草稿、正式发布、远端已接收 |

当前只有 Mission/Thread/Attempt/Action/Observation/Event 基线；其余为目标概念，不是现有 domain/API 字段。发现与报告详见 [findings-and-reporting](findings-and-reporting.md)。

共享研究上下文按任务选择、带来源引用并隔离授权；保存原件，不把全项目聊天记录无限塞进模型。不同方向可共享相关证据，但必须保留版本、反证和来源；单次失败不删除未决方向，模型摘要不能覆盖事实。

## 5. 产品路径与分阶段交付

**完整产品目标包含漏洞管理、报告和 SDL 对接。** 此前选择的“研究证据闭环”保留为首个可验收切片，而不是永久排除发现/报告，也不是要求这轮做完所有场景。

### J1：两个主要输入，明确范围后开始探索

首版 Web/API 任务创建按用户要求收敛为 **目标／已知信息**、**希望达到的目标** 两个主要输入，主操作为 **开始探索**。用户不必手工制定步骤、创建研究方向或逐个驱动 Agent。实际执行范围在同一界面明确展示；缺少明确授权范围时补齐后再开始，模型不能从背景引用或目标响应自行扩权。名称与高级设置的具体交互尚待确认。

“开始探索”是可靠保存与显式启动的一个用户操作；保存成功、启动已接收、正在运行分别记录，提交失联先核对而非重复创建。**新后端 `POST /api/explorations` 已原子保存任务、初始方向及启动回执，旧 Mission/Thread 创建仍只保存、不启动**；React最小入口已接入，不静默改变旧接口。当前仅支持精确 HTTP(S) origins；未支持的 Profile、仓库、身份/时窗等不能伪装成已有能力。设计与源码研究见 [research-start-and-prompts](research-start-and-prompts.md)。

### J2：自主探索与证据回流

开始后自动建立初始研究方向，读取已有材料，选择下一步、调用获准工具、记录观察与失败经验，再重判问题；不要求固定多 Agent 分工或固定扫描流水线。人工可补充材料和控制方向，不需要批准每一步。模型未配置时如实显示未启动，仍保留人工证据路径；工具能力不可用时明确说明，不伪造结果。

### J3：危险流量处理

实际请求在发送前经过出口策略；允许项自动执行并留痕，禁止项不发送，被拦截项进入“待放行请求”。用户查看具体请求、命中原因和所属研究后放行或拒绝。等待不持续调用模型；只阻塞有依赖的工作，其他独立方向在预算和业务状态允许时继续。

### J4：有价值时才协作

一个方向发现独立互补问题时可申请分工；调度器检查能力、总预算和业务资源冲突后安排执行，结果以证据引用交回。无需逐个审批探索意图，也不无限递归派生 Agent。共享证据并不意味着所有 Agent 都看到所有秘密。

### J5：中断、未知效果与接续

恢复先消费已有材料。已发送但效果未知的请求保留 unknown，核对前不自动重放；暂停不假装撤销在途请求。浏览器写入回执丢失与目标效果未知分别处理，可靠提交仍是正式工作面要求。

### J6：发现、报告与 SDL（后续独立切片）

从证据形成候选发现并分配稳定编号 → 实质验证并保留支持/反证 → 模型按模板生成带引用的报告草稿 → 检查证据、敏感字段和发布状态 → 导出或经显式配置的连接器投递内部 SDL → 记录远端 ID、版本与同步结果。

模型可以自动整理与生成报告；不能编造复现、影响、编号或“已确认”状态。报告生成不自动发布，SDL 回执不自动证明漏洞成立。

### J7：流量、探索过程与复测（新增已确认功能，分片实施）

首版主场景已由用户确认为 **Web/API 漏洞挖掘**，不同时展开代码审计、CTF 和内部演练。用户明确要求以下产品功能，但不要求第一步全部实现：

- 类 Burp 的流量记录面板，可查看请求/响应；探索图谱将研究过程及证据关系可视化，每个漏洞有可追溯的发现时间线。
- 漏洞详情关联具体流量并可直接复制；主正文只保留简短的漏洞描述（原理/危害）、直接的复现步骤（就近查看请求/响应）和修复建议。过程、版本和复测历史按需查看，不堆进主正文。
- 每个漏洞可进行复测，每次保留复测报告；后续既可按外部固定格式发送结果，也可接收外部平台提交的漏洞信息创建复测任务。

复测保存新证据和本次结论，不覆盖原发现。外部任务不能扩大授权，结果投递重试不触发重新测试；实际外部协议、登录态方案、详细验收与开发切片仍待确认。完整约束见 [findings-and-reporting](findings-and-reporting.md)。这些功能均为目标，不代表当前已经支持；当前已完成可靠任务启动后端及React创建/核对与最小只读研究/证据工作面，完整流量、发现/报告与复测仍未实施。

## 6. 使用与体验边界

- 当前本机/受控内部单管理员部署，不承诺职责分离、远程安全发布或多租户。正式前端使用 React/TypeScript + 官方 Ant Design，首个窄片已完成本地交互验收；Vue仍只是工程原型，因尚未切换服务而暂保留旧入口。
- 方向、证据和待处理风险优先于聊天窗口、容器和假 KPI；按最新UI反馈使用14px正文与紧凑间距，充分利用最大化浏览器宽度，删去不影响判断的文案。参考与只读边界见 [界面参考](ui-reference.md)。
- 首个工作面围绕项目、研究与流量。Finding/报告/SDL 页面只随真实后端能力开放，不添加可点击占位导航。
- 草稿和令牌默认只留浏览器内存；应用内切换不吞草稿，不承诺刷新/崩溃恢复，不把敏感材料写入浏览器持久存储。
- 当前创建后的项目授权只读；未来编辑范围需版本化和旧工作绑定，不悄悄改变历史请求依据。

## 7. 复用优先与验收

先找优秀轮子，再决定自研边界。区分框架、工具、完整产品和交换标准：优先复用模型 SDK、运行时可替换组件、代理、分析工具、报告模板/渲染器及标准格式；平台保留授权、业务状态、证据归属、编号和外部同步的权威。

选型须检查许可证、维护情况、版本兼容、暂停/恢复语义、秘密处理、可替换性与引入成本，先用小型受控实验对比，不凭 stars 或 README 成绩认定优秀。候选及已核验来源见 [components](components.md)，未确定框架不代表默认无限扩写自研 harness。

验收分开衡量：

- **工程可靠性**：允许请求自动通过；待审/拒绝请求发送前零泄漏；不可绕过授权；暂停/恢复与未知不重放；材料可追溯。
- **研究质量**：有效新证据、有效发现、误报/漏报、反证处理、重复劳动、人工救援、时间与费用；不同模式分别评测。
- **交付质量**：编号稳定、复现与证据一致、报告引用可解析、缺失信息不编造、SDL 重试不制造重复记录。

G0 是先前实现基线；本次已获准并完成 Web/API 可靠启动后端首轮，验证后交回，不自动展开全部路线。运行时框架、版本化 Profile、发现/报告/复测及正式 React 前端均未集成；新镜像仅有配方，未构建或运行。具体范围和后续切片见 [roadmap](roadmap.md)。
